# Codex项目记忆系统实践

## 背景

在 `D:\powerbi项目` 中，项目已经形成了一套适合多 Codex 窗口协作的“项目记忆系统”。这套机制的目标是解决多个 AI 对话窗口并行工作时，记忆分散、规则冲突、后续窗口不知道该读哪段上下文的问题。

这对个人可生长知识库很有参考价值：Obsidian 不只是存资料，也可以承接 AI 协作后的长期规则、项目上下文、变更记录和复盘。

## 记忆分层模型

### L1 主记忆

主记忆只保存：

- 项目是什么。
- 当前最终表和核心口径。
- 当前有效规则摘要。
- 任务路由。
- 哪类任务读哪个模块。
- 最近关键变更。

主记忆不应该保存：

- 大段 SQL。
- 一次性排查过程。
- 旧错误尝试。
- 临时结果明细。

### L2 稳定规则与模块记忆

模块记忆保存稳定业务规则、表结构、脚本、主键、业务口径、特殊处理逻辑。

示例模块：

- Mapping
- 利润主链路
- 成本
- Coop
- Ads / Promo
- Inventory / Storage
- 脚本刷新
- 数据质量检查
- 特殊规则
- 数据治理

### L3 当前状态

当前状态只保存会随刷新变化的数字：

- 行数
- 金额
- 日期覆盖
- 缺失数量
- 质量检查结果

原则：动态状态不要散落在多个笔记里复制成多个“当前值”，否则后续很容易互相冲突。

### L4 变更与窗口记忆

每个 AI 对话窗口或阶段任务都可以单独建立窗口记忆，记录：

- 本次任务目标
- 读取过的记忆
- 输入文件或用户补充
- 执行动作
- 输出文件 / 表
- 校验结果
- 新增长期规则候选
- 已合并到哪些模块
- 待办和风险

### L5 Inbox

Inbox 用于临时存放还没整理的片段，但不能长期堆积。每次主任务结束时要判断哪些内容值得进入模块，哪些只作为历史归档。

### L6 Archive

Archive 存放过期规则、历史窗口和旧排查，不参与新任务默认读取。

## 信息进入哪里的判断

| 信息类型 | 推荐位置 |
| --- | --- |
| 用户临时想法、待确认假设 | 窗口记忆 |
| 一次性 SQL 结果 | 窗口记忆或归档 |
| 新表、新字段、新存储过程 | 对应模块 + 主索引摘要 |
| 稳定业务规则 | 对应模块 + 主索引摘要 |
| 规则状态和正式依据 | 规则总表 |
| 行数、金额、最大日期、缺失数量 | 当前状态快照 |
| 已执行的口径变更 | 变更单 + CHANGELOG |
| 人工补录、时效切换、硬编码例外 | 特殊规则模块 |
| 文件路径、长期脚本 | 对应模块 |
| 错误尝试、误操作修正 | 窗口记忆；如有长期教训再写模块 |

## 规则生命周期

一条规则不应该直接从“想到”变成“当前有效”。更稳妥的状态流转是：

1. `proposed`：已提出，尚未确认或实现。
2. `approved`：用户已确认，等待实现。
3. `implemented`：代码和数据库已修改，但尚未完成全量验收。
4. `active`：已实现、回填 / 刷新并验收通过，是当前正式规则。
5. `deprecated`：已被新规则替代，保留历史追溯。
6. `rejected`：明确不采用。

只有 `active` 规则可以写入主索引的“当前有效规则”。

## 规则变更必答问题

每次规则变化至少要回答：

- 旧规则是什么？
- 新规则是什么？
- 为什么改变？
- 影响哪些源数据、表、SQL/Python、Power BI 和调度？
- 粒度和主键是否变化？
- 是否需要回算历史？
- 哪些指标必须守恒？
- 如何回滚？
- 验收结果是什么？

## 对我的个人知识库的启发

以后使用 Codex + Obsidian 时，可以采用类似模式：

- 用 `00-个人档案` 放我的长期定位和能力画像。
- 用各专题目录放稳定知识和方法论。
- 用 `09-项目案例库` 放项目复盘和可展示案例。
- 用 `12-AI对话沉淀` 放每次 AI 协作形成的结论、提示词、规则和复盘。
- 用 `99-收件箱` 暂存未整理资料。

每次和 AI 完成一个重要任务后，不只是保留聊天记录，而要让 AI 帮我回答：

1. 这次产生了什么长期知识？
2. 哪些只是临时过程？
3. 哪些规则以后会复用？
4. 应该合并到哪个专题笔记？
5. 是否需要创建项目复盘？
