# 项目文件与记忆治理方法

## 1. 这套方法要解决什么问题

项目持续推进后，最容易出现四类问题：

1. 正式代码、临时脚本、原始数据和生成结果混在一起。
2. 当前规则、历史上下文和一次性排查记录互相覆盖。
3. 新窗口不知道应该先读什么，检索时只能靠文件名和记忆。
4. Git 改动没有经过分类，最后无法判断哪些应该提交、归档或舍弃。

治理的目标不是让目录看起来整齐，而是让每个文件都能回答四个问题：

- 它是什么性质？正式、临时、历史还是系统文件？
- 谁使用或维护它？本地、远程、共享还是外部？
- 它是否具有权威性？规则、输入、生成结果、过程文件还是冻结证据？
- 如果要继续处理这个问题，应该从哪里开始检索？

## 2. 文件治理的三维分类

每个新文件先按三个维度判断，再决定目录和生命周期。

| 维度 | 分类 | 判断方式 |
|---|---|---|
| 成熟度 | `formal` 正式 | 会长期复用，进入项目正式流程 |
| 成熟度 | `temporary` 临时 | 一次性排查、试算、渲染或中间文件 |
| 成熟度 | `historical` 历史 | 不再作为当前依据，但需要追溯 |
| 成熟度 | `system` 系统 | 工具、运行时或平台自动生成 |
| 运行范围 | `local` 本地 | 只在本地运行或维护 |
| 运行范围 | `remote` 远程 | Linux、Airflow、服务器运行 |
| 运行范围 | `shared` 共享 | 本地与远程共同使用，或团队共同维护 |
| 运行范围 | `external` 外部 | 第三方、外部交接或外部平台拥有 |
| 权威性 | `canonical` 权威 | 规则、配置、正式代码或唯一状态入口 |
| 权威性 | `input` 输入 | 原始业务文件、人工维护表、外部导出 |
| 权威性 | `generated` 生成 | 可由脚本重建的报告、缓存和预览 |
| 权威性 | `working` 工作 | 过程记录、临时试算、待整理材料 |
| 权威性 | `frozen` 冻结 | 历史审计、外部原件、已退役版本 |

目录的 `lifecycle` 再补充文件如何更新：`permanent`、`append_only`、`replace_latest`、`regenerable`、`frozen`、`clear_each_task` 等。

## 3. 项目目录的放置规则

| 文件类型 | 位置 | 管理原则 |
|---|---|---|
| 正式本地 Python | `scripts/final/local/` | 长期逻辑唯一维护入口 |
| 正式 Linux/Airflow Python | `scripts/final/linux/` | 只从远程安全配置读取凭证 |
| Windows 启动入口 | `scripts/final/windows/` | 只做编排，不写业务逻辑 |
| 正式 SQL | `sql/` | 有序编号、可追溯、同步检查 |
| 自动化测试 | `tests/` | 只验证正式逻辑和治理合同 |
| 一次性排查脚本 | `tmp_scripts/` | 以 `tmp_` 开头，稳定后迁入正式目录 |
| 临时缓存/渲染产物 | `tmp/` | 每个任务结束后清理明确文件 |
| 原始业务输入 | `资料/`、`cost/`、`map/handoff_package/01_原始人工录入表/` | 只读保留、保留来源和批次 |
| 生成报表 | `output/`、`outputs/` 等已登记目录 | 可重建，不作为源数据 |
| 线上材料 | `online/` | 只放部署、调度、runbook 和非敏感模板 |
| 正式项目文档 | `docs/` | 规则、操作手册、治理方法和汇报成品 |
| 外部交接原件 | `外部交接/` | 冻结参考，生产逻辑需另行迁移 |

任何目录变化都要同步登记到 `config/project_folders.json`，任何文件类型和检索路由变化都要同步到 `config/project_governance.json` 与 `项目记忆/memory_system/07_文件与记忆检索索引.md`。

pytest 的正式测试入口由根目录 `pytest.ini` 限定为 `tests/`；`scripts/final/local/` 中带有 `test_` 命名的运维连通性脚本不属于自动化测试集合，避免被误收集。

## 4. 记忆架构和权威顺序

当前记忆系统采用“入口—规则—状态—模块—过程—变更”的分层结构：

| 文件/目录 | 作用 | 是否默认读取 |
|---|---|---|
| `00_主记忆索引.md` | 新窗口入口和任务路由 | 是 |
| `01_记忆合并规则.md` | 多窗口信息如何合并 | 修改记忆时读取 |
| `02_规则生命周期.md` | 规则编号、状态、退役和替代 | 修改规则时读取 |
| `03_当前状态快照.md` | 动态数据库状态唯一入口 | 查当前状态时读取 |
| `04_口径与术语字典.md` | 渠道、粒度、指标统一定义 | 口径问题时读取 |
| `05_规则总表.md` | BR/DQ/SR 规则登记册 | 规则问题时读取 |
| `06_待办事项总表.md` | 当前待办唯一入口 | 查询待办时读取 |
| `07_文件与记忆检索索引.md` | 文件位置、分类和检索路线 | 文件治理时读取 |
| `modules/` | 稳定业务模块规则 | 按任务读取 |
| `changes/` | CR 变更单和月度日志 | 追溯规则变化时读取 |
| `windows/` | 任务过程和验收证据 | 延续具体任务时读取 |
| `archive/` | 已退役规则和历史记忆 | 非默认，追溯时读取 |

权威顺序如下：

1. 用户最新确认和当前数据库实值。
2. 当前状态快照。
3. 规则总表、术语字典和对应模块。
4. 正式代码、SQL 和质量检查结果。
5. 变更单、月度日志和窗口证据。
6. 历史快照、旧根层文件和历史报告。

历史文件不能覆盖当前规则。正式规则过期时使用 `deprecated` 或 `superseded`，记录替代规则和原因，不直接删除。

## 5. 每次治理的标准过程

### 第一步：建立问题边界

先明确本次治理是在处理：目录、文件、记忆、规则、代码、数据源还是 Git 改动。避免把一次性排查误升级为正式规则，也避免把正式规则只写在窗口记忆里。

### 第二步：只读盘点

盘点以下内容：

- 根目录和治理目录是否出现未登记文件。
- 记忆文件是否存在重复、冲突、旧路径或过期状态。
- 规则编号是否重复，变更单是否有来源和验收。
- 历史文件是否仍被当前文档、脚本或待办引用。
- Git 中哪些是已修改、未跟踪、被忽略或无关改动。

### 第三步：分类处理

- 当前有效内容：合并到正式入口、模块或规则总表。
- 临时过程：保留在 `windows/` 或 `tmp_scripts/`，完成后清理可重建产物。
- 历史证据：保留并明确“非默认读取”，必要时单文件迁入 `archive/`。
- 重复内容：先确认是否为兼容摘要；真正重复的内容才合并或删除。
- 旧规则：改为 `deprecated` / `superseded`，不能静默删除。
- 明确无价值的占位项：单文件删除，并记录清理原因。

### 第四步：同步索引

任何正式变更至少同步：

- 主记忆索引。
- 对应模块或规则总表。
- `07_文件与记忆检索索引.md`。
- 变更单和月度 CHANGELOG。
- 当前待办或当前状态快照（如果受影响）。
- 项目 README、`agent.md` 或操作手册（如果入口发生变化）。

### 第五步：验证

按变更范围运行：

```powershell
python scripts/final/local/audit_project_structure.py
python scripts/final/local/audit_project_file_governance.py
python scripts/final/local/audit_memory_consistency.py
python scripts/final/local/audit_weekly_memory.py
python scripts/final/local/audit_project_governance.py
python -m pytest tests -q
```

验证结果必须写入窗口记忆或变更单。Git safety 如果只是因为工作区尚未提交而失败，应单独记录，不能误判为业务治理失败。

## 6. Git 改动统一治理流程

每次提交前按以下顺序处理：

1. `git status`：列出全部修改和未跟踪文件。
2. `git diff --stat`：判断改动规模和主题。
3. `git diff -- <path>`：逐个确认改动意图，保护用户已有修改。
4. 按主题分组：代码、SQL、测试、规则/记忆、目录治理、文档。
5. 删除或移动前确认引用关系；不批量删除目录或文件。
6. 运行治理审计、测试和 `git diff --check`。
7. 再次检查 `git status`，确认没有凭证、原始数据、缓存和无关文件。
8. 使用单一清晰提交说明提交本批变更；提交后记录 commit id 和验证结果。

建议的提交说明格式：

```text
治理：统一项目文件、记忆索引与审计门禁
```

如果一次工作包含互不相关的业务修复，应拆成多个提交；本次连续治理产生的结构、记忆、索引、审计和测试改动可以作为一个治理批次提交。

## 7. 周期性治理清单

每周至少检查一次：

- 新增根目录文件和未登记目录。
- `tmp/`、`tmp_scripts/`、`memory_system/inbox/` 是否有应清理内容。
- 根层旧记忆是否仍被误当成当前规则。
- `05_规则总表.md` 是否有重复编号或未登记状态。
- `06_待办事项总表.md` 是否存在空占位、重复待办或已完成但仍 open 的事项。
- 变更单、CHANGELOG、窗口记录和当前规则是否一致。
- `online/` 是否出现真实凭证、token、私钥或大体积日志。
- Git 是否存在未提交的正式改动、未跟踪文件或敏感文件。

- 正式记忆一致性、目录结构、文件治理和周检审计脚本。
- 53 项正式测试通过。
- 根层旧记忆已明确为当前入口、兼容摘要或历史参考，不再混用。
