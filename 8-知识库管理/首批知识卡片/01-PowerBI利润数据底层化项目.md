# Power BI 利润数据底层化项目｜知识卡片

## 一句话结论

将原本散落在 Power BI、人工文件和数据库中的 Amazon VC 利润计算逻辑迁移到 PostgreSQL 数据底层，形成可追溯、可校验、可扩展的利润计算链路。

## 资料解决的问题

重点解决多来源数据口径不一致、手工 Mapping 污染、销售与供货口径混用、成本与费用归集困难、分摊结果不可验证等问题。

## 核心方法

1. 先定义业务口径，再做技术实现。
2. 区分终端销售、供货结构、共享基础数据和渠道专属事实。
3. 以 `date + asin` 为当前粒度，以标准 ASIN 合集构建 profit spine。
4. 对销售、广告、促销、Coop、库存、仓储费进行清洗、匹配、分摊和校验。
5. 通过金额守恒、唯一键、缺失、渠道标签和分摊结果进行质量验收。
6. 将项目记忆、规则变更和状态快照纳入数据项目治理。

## 对我的价值

- 这是当前最重要的跨境电商 BI / P&L 项目主案例。
- 可以支撑“从 0 到 1 建设数据底座”“如何解决口径争议”“如何把 BI 逻辑下沉数据库”等面试问题。
- 能连接 Mapping、成本、Coop、广告、促销、库存和数据治理多个主题。

## 与已有知识的关系

- 与 Power BI 数据平台七步框架互补：本卡是具体项目案例，七步框架是通用方法论。
- 与 P&L 利润链路、COGS、Coop 笔记构成同一条利润主链路。
- 不应把来源中的计划扩展自动表述为已经完成的生产能力。

## 需要验证的内容

- 当前最终表和粒度是否仍是最新状态。
- 数据库对象、刷新步骤和质量规则是否与外部 `D:\powerbi项目` 一致。
- 项目结果中哪些是个人主导、哪些是团队协作。
- 是否有可公开表达的效率、准确率、金额或周期结果。

## 最小实践任务

画出一张“源数据 → 清洗 / Mapping → 利润 spine → Power BI → 质量校验”的链路图，并为每一步标注输入、输出、粒度、主键和验收规则。

验收标准：

- 能解释为什么 VC terminal/endpos 与 PO/DF/DI 不能混算。
- 能指出广告和促销为什么必须先聚合再 Join。
- 能列出至少 5 个利润表验收检查点。

## 我的最终判断

这不是单纯的 Power BI 报表项目，而是一个以利润为核心的数据底座治理项目。后续最值得继续沉淀的是“事实粒度、主键、来源血缘、分摊规则、金额守恒和业务验收”六个方面。
