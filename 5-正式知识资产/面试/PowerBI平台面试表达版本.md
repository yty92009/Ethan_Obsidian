# 多平台跨境电商 Power BI 平台｜面试表达版本

> 本文件是面试表达草稿。涉及具体数字、团队边界、项目结果和上线状态时，必须回到原始经历确认，不得为了完整而编造。

## 一、30 秒版本

如果从 0 到 1 搭建跨境电商 Power BI 平台，我不会先做图，而是先搭数据底座。整体会按七步推进：先盘点并接入 ERP、平台、广告、库存、财务和人工表等数据源；再做落库、清洗和标准化；然后统一 SKU、ASIN、父子 SKU、Kit、指标口径和费用分摊；接着做 ODS、DIM、DWD、DWS、ADS 分层和 Power BI 星型模型；上线后重点做好 T+1 刷新、权限、数据质量和持续运营。核心目标是让业务每天看到可信、可追溯、能支持经营决策的数据。

## 二、1 分钟版本

我理解的跨境电商 BI 平台建设，不是单纯做几张 Power BI 报表，而是建设一套经营数据体系。第一步我会先盘点数据源，包括 Amazon VC/SC、ERP、财务、广告、库存、促销、费用和人工维护表，并根据实际情况选择 API、后台导出、RPA、Python 或固定模板接入。第二步是将数据稳定落库，保留来源、批次、日期范围和导入记录，解决字段、日期、币种、重复和缺失问题。第三步是做业务关系和指标口径治理，统一 SKU、ASIN、父子 SKU、Kit、平台、店铺、供应商、负责人和费用分摊规则。之后再按 ODS、DIM、DWD、DWS、ADS 分层，把复杂逻辑尽量放在数据库或数仓中，Power BI 主要负责星型模型、度量值、筛选和展示。最后通过 T+1 刷新、RLS 权限、质量检查、源系统对账和反馈机制，让平台能够长期稳定使用。

## 三、2 分钟版本

我会把这个项目当成经营数据平台建设，而不是报表开发项目。

第一步是数据采集，先把 ERP、财务系统、Amazon VC/SC、广告、库存、费用、促销和人工表等来源摸清楚，再根据接口条件选择 API、后台下载、RPA、Python 或固定模板。跨境电商中有些数据没有标准 API，人工下载和维护表客观存在，所以关键是把它们纳入统一的批次、留痕和质量流程。

第二步是落库、清洗和技术标准化，统一字段、日期、时区、币种、金额、数量和编码，处理重复、空值、异常值和文件结构变化，同时保留源文件、批次和导入日志。第三步是业务关系和经营口径治理，解决“看的是谁、怎么算、分到谁”三个问题。例如 SKU、ASIN、父子 SKU、Kit、平台、店铺、供应商和负责人要统一映射；销售、成本、广告、促销、仓储和利润要明确计算口径；不能直接匹配到产品和渠道的费用要有可追溯的分摊规则。

第四步是数仓分层，把原始数据放在 ODS，主数据和 Mapping 放在 DIM，标准明细放在 DWD，主题汇总放在 DWS，面向 Power BI 和预警的应用数据放在 ADS。这样可以让数据链路可追溯，复杂清洗、映射、分摊和利润计算不会全部堆到 Power BI 里。

第五步是 BI 建模，通常采用星型模型，用共享维度关联销售、广告、库存、费用、成本和退货事实表，Power BI 层主要做 DAX 度量、同比环比、占比、排名、动态筛选和钻取。第六步是 T+1、权限和质量，保证业务每天上班能看到最新数据，并按平台、店铺、产品线、SKU 和负责人实现可见范围控制，同时检查文件到达、重复导入、Mapping 缺失、成本缺失、金额守恒和源系统对账。最后通过需求池、口径文档、版本管理、刷新监控和业务反馈持续运营。

## 四、项目案例连接版

在具体项目中，我曾将原来分散在 Power BI、人工文件、数据库源表和业务规则中的 Amazon VC 利润计算逻辑逐步下沉到 PostgreSQL。这个项目的难点不是单独写 SQL，而是要把销售、成本、广告、促销、Coop、库存、尺寸和 SKU Mapping 的来源、粒度、匹配和分摊关系理清楚。当前利润链路以标准 ASIN 合集构建利润承载表，再按销售、成本、Coop、促销、广告、库存和仓储费的依赖关系逐步加工，并通过唯一键、金额守恒、渠道隔离和缺失检查验收。这个经历体现的是数据底座治理和经营利润模型建设能力，而不是简单制作报表。

## 五、常见追问

### 1. 为什么不把所有逻辑放在 Power BI？

复杂清洗、主数据映射、费用分摊和利润计算需要复用、追溯、重跑和对账。如果全部放在 Power BI，容易造成刷新压力、模型重复和口径不一致。因此我会将稳定的底层逻辑尽量放在数据库或数仓，Power BI 重点负责语义模型、度量值和交互展示。

### 2. 如何保证利润数据可信？

先定义销售、成本和费用口径，再保留来源和批次；对 Mapping、主键、日期、缺失和重复做质量检查；对销售、广告、促销和仓储分摊做金额守恒；对平台、ERP、财务账单和最终结果做对账；最后记录异常、处理人和验收结果。

### 3. Amazon VC 的销售和 PO/DF/DI 如何处理？

VC terminal/endpos 是终端销售口径，作为 SalesAmt 主事实；PO、DF、DI 是供货结构，用于 Coop 和成本权重估算，不能与终端销售额直接相加。建模时要保留口径边界，并在渠道专属结果层明确继承规则。

### 4. 如何处理人工 Excel？

不把它当成临时文件，而是纳入生产化管理：固定目录和模板、文件哈希、批次号、来源留痕、日期范围和字段校验、重复导入检查、错误反馈和质量状态。这样人工来源也能被追溯和复跑。

### 5. 如何做权限？

根据平台、账号、店铺、站点、产品线、品类、SKU 和负责人建立权限映射表，再结合 Workspace、App 和 RLS 控制范围。人员或负责范围变化时维护映射表，尽量不修改报表逻辑。

### 6. 如何判断平台上线？

不能只看页面是否完成。还要确认指标口径、源系统对账、刷新稳定性、权限测试、异常提示、用户使用说明、反馈机制和版本记录都已具备。

## 六、表达边界

可以说：

> 我具备从业务目标、数据源、主数据、指标口径、数仓分层、BI 建模到刷新、权限和质量运营的完整方法，并在 Amazon VC 利润项目中实践了其中的核心链路。

不要在未经确认时说：

- 所有平台都已经接入。
- 所有 Agent 或 RAGFlow 方案都已经生产部署。
- 所有结果都是个人独立完成。
- 项目一定取得了未经记录的金额或效率提升。
