# 多平台跨境电商 Power BI 数据平台从 0 到 1 搭建流程

## 一句话定位

多平台跨境电商公司的 Power BI 数据平台建设，本质不是“做几张报表”，而是围绕经营决策建立一套可信的数据底座、统一指标口径、稳定刷新链路、权限体系和业务使用机制。

面试时可以这样概括：

> 我理解的从 0 到 1 搭建 BI 平台，不是先打开 Power BI 做图，而是先把业务目标、数据源、主数据、指标口径和刷新机制梳理清楚。尤其跨境电商多平台场景，Amazon VC、SC、ERP、广告、库存、费用、促销、人工维护表都可能影响利润结果。如果前面的数据底座和口径不稳，报表越多反而越容易造成争议。所以我会按“业务场景梳理 - 数据源盘点 - 主数据治理 - 数仓分层 - 语义模型 - 报表体系 - 权限发布 - 数据质量 - 运营迭代”的路径推进。

## 通用建设框架：7 步总流程

这套框架适合面试时先讲全局，再根据面试官追问展开细节。

### 第一步：数据采集

背景：大多数公司的数据是分散在不同业务系统里的，比如业务数据在 ERP，财务数据在财务系统，再加上人工表、线上导出表等，整体数据比较零散、分散。

目的：把这些零散的数据来源摸清楚，根据不同数据源选择 API、爬虫、自动化程序、RPA、后台导出、人工维护等方式，建立稳定的数据采集链路，为后续搭建数据底座做基础。

---

### 第二步：数据落库、清洗与技术标准化

背景：不同来源的数据拿回来以后，字段名称、文件格式、日期格式、币种格式、数字格式、编码格式都不一样，同时还会有空值、重复数据、异常值、字段缺失、文件日期选错等问题。

目的：先把原始数据稳定落库，并处理成结构干净、格式统一、字段可用、来源可追溯的标准明细数据。第二步重点解决“数据能不能正常用”的问题，不在这一层决定复杂业务口径。

---

### 第三步：业务关系与经营口径治理

背景：数据清洗完成后，真正影响 BI 平台可信度的，是产品关系和业务口径能不能统一。比如同一个产品在不同平台可能有内部 SKU、平台 SKU、ASIN、MSKU 等多套编码，也会有父 SKU 和子 SKU、组合品 SKU 和组成单品 SKU 这类关系。跨境电商里还有很多费用或数据无法直接匹配到具体的渠道 + 产品，需要建立合理的分摊规则。

目的：通过产品关系治理、指标口径统一和分摊规则设计，把“看的是谁”“怎么算”“分到谁”这三个问题解决清楚。这里才处理 SKU、ASIN、父子 SKU、组合品和单品、店铺、平台、供应商、品类、负责人等映射关系，以及销售、成本、费用、利润、库存、广告等核心指标的计算规则、数据来源、适用范围和费用分摊逻辑。第三步重点解决“业务含义能不能统一”的问题。

---

### 第四步：数仓分层和主题数据集建设

背景：如果所有清洗、映射、计算、分摊和汇总逻辑都堆在 Power BI 报表层，后续复用、对账、重跑和维护成本都会很高。一旦数据出错，也很难判断问题出在源数据、清洗规则、映射关系、指标公式，还是报表展示层。

目的：按 ODS、DIM、DWD、DWS、ADS 分层沉淀稳定的数据底座和经营分析主题。分层的好处是让数据链路更清楚，方便快速定位问题；把复杂逻辑前置到数据库或数仓层，减少 Power BI 加载的数据量；同时提升报表使用体验、刷新稳定性和查询效率。

---

### 第五步：BI 数据建模及报表开发

背景：数据底层已经完成清洗、映射、分摊和主题汇总后，BI 层不应该再承担大量前期加工逻辑。BI 层更重要的是建立清晰的数据模型，通过主数据维度去关联销售、库存、广告、费用、成本、退货等不同业务主题的事实表，并在统一模型上开发报表。

目的：用星型模型搭建稳定、可复用的 BI 数据模型，维度表负责筛选、分组和下钻，事实表负责承载业务数据和指标计算基础。好的 BI 平台应该把数据清洗、映射、分摊、汇总等前期加工放在数据底层完成，BI 层主要做高级度量、同比环比、占比、排名、动态筛选、钻取分析和报表开发，从而提升报表性能、口径一致性和使用体验。

---

### 第六步：T+1 更新、权限控制与数据质量校验

背景：平台上线后，业务不只是希望“有报表”，而是希望每天上班就能看到最新数据，及时判断昨天的销售、利润、库存、广告和费用变化。同时，不同渠道、不同产品线的运营只能看到自己负责范围内的数据，不能所有人都看到全公司明细。

目的：建立稳定的 T+1 更新机制，保证每天上班前完成核心数据刷新；通过权限控制，让不同渠道、产品线和负责人只看到自己负责的数据；同时配合数据质量校验，保证异常能发现、结果能对账、数据能被业务信任。

---

### 第七步：上线运营、业务反馈和持续迭代

背景：BI 平台上线后，业务、指标、权限、报表和管理需求都会持续调整。

目的：通过需求池、版本管理、口径维护和反馈机制，让平台长期可用。

口述提纲：

```text
数据采集 -> 落库清洗和技术标准化 -> 业务关系和经营口径治理 -> 数仓分层 -> BI 数据建模及报表开发 -> T+1 更新、权限控制与数据质量校验 -> 上线运营迭代
```

### 30 秒版本：快速回答

> 如果从 0 到 1 搭建跨境电商 BI 平台，我不会先做图，而是先搭数据底座。整体会按 7 步推进：先做数据采集，把 ERP、财务系统、平台导出表、人工维护表这些零散来源接起来；再做落库清洗和标准化；然后统一 SKU、ASIN、父子 SKU、组合品、指标口径和分摊规则；接着做数仓分层、BI 星型模型和报表开发；上线后再做好 T+1 更新、权限控制、数据质量校验和持续迭代。核心目标是让业务每天看到可信、可追溯、能决策的数据。

## 7 步框架详解

### 第一步：数据采集

目标：

把零散分布在不同业务系统、人工表和线上导出表中的数据源摸清楚，并通过 API、爬虫、自动化程序、RPA、后台导出、人工维护等方式建立稳定的数据采集链路，为后续数据底座建设做基础。

跨境电商常见来源：

- 电商平台：Amazon VC、Amazon SC、Walmart、Wayfair、Shopify、独立站等。
- 广告平台：Amazon Ads、Google Ads、Meta Ads、平台站内广告等。
- 业务后台：订单、库存、Listing、Buy Box、评论、退货、促销、Coupon。
- ERP / 财务系统：NetSuite、采购成本、发票、账单、费用、供应商、汇率。
- 仓储 / 物流系统：WMS、FBA 库存、海外仓、在途、尾程运费。
- 线下或人工数据：Excel、CSV、共享文件夹、邮件附件、人工维护映射表、目标表、成本表。

常见采集方式：

- API 接入：适合平台、ERP、广告、库存等有接口的数据源。
- 爬虫采集：适合没有正式接口，但网页结构相对稳定、需要定期抓取的数据。
- 自动化程序：适合批量下载、批量整理、定时拉取、自动入库等重复流程。
- RPA 采集：适合必须登录后台、点击下载、操作路径固定但缺少接口的场景。
- 后台导出：适合 Amazon VC / SC、广告后台、平台账单等需要人工或半自动下载的报表。
- 人工维护：适合成本表、目标表、映射表、特殊调整表等需要业务持续维护的数据。

要点：

- 不同来源的数据采集方式不同，不能假设都有 API。
- 后台下载、RPA 抓取、人工维护和系统接口都要纳入统一流程。
- 对 Amazon VC，要区分 Vendor Central、Seller Central、PO、DI、DF、Retail Sales 等不同业务口径。

阶段产出：

- 数据源清单
- 数据获取方式清单
- 更新频率清单
- 数据负责人清单
- API / 爬虫 / 自动化采集任务清单
- 手工文件模板和上传规范

面试表达：

> 我会先做数据源盘点，把不同平台、不同业务系统、线上线下数据都列出来。能通过 API 接的，就优先用 API；没有接口但规则稳定的，可以通过爬虫、自动化程序或 RPA 采集；只能人工维护的，比如成本表、目标表、映射表，也要设计固定模板和上传流程。跨境电商里很多数据不一定有 API，关键是把这些来源都纳入稳定采集链路，而不是临时文件。

### 第二步：数据落库、清洗与技术标准化

目标：

把采集到的数据稳定落库，保留来源、批次、文件名、导入时间和日期范围，并把原始数据处理成结构干净、格式统一、字段可用的标准明细数据。

边界说明：

第二步主要解决技术层面的“数据能不能正常用”。例如字段名能不能统一、日期能不能识别、金额是不是数字、文件有没有重复、关键字段有没有空值、异常值能不能识别。它不负责决定父子 SKU 怎么归集、组合品怎么拆、利润怎么算、费用怎么分摊，这些放到第三步。

关键设计：

- 每次导入生成 batch_id。
- 保留 source_system、source_platform、account、marketplace。
- 保留 source_file_name、imported_at、report_start_date、report_end_date。
- 文件导入要做重复校验。
- 手工文件要保留原始文件。
- API 数据要保留拉取时间和参数。

阶段产出：

- ODS 原始表
- 导入日志表
- 文件批次表
- 导入失败记录
- 数据到达监控

面试表达：

> 我会先把源数据稳定入库，而且一定要保留批次和来源。因为后面如果利润、费用或库存数据被质疑，必须能追溯到是哪一天、哪个平台、哪个账号、哪个文件或接口来的。

#### 清洗与技术标准化

目标：

把不同来源的数据转换成统一格式，为后续建模和分析做准备。

常见处理：

- 字段命名统一。
- 日期格式统一。
- 币种和金额格式统一。
- SKU、ASIN、店铺、平台等字段做技术标准化，例如去空格、统一大小写、统一字段类型、统一空值格式；不在这一层决定业务映射关系。
- 数量、金额、百分比字段类型转换。
- 删除重复数据。
- 处理空值、异常值、负数、撤销单、退款单。
- 统一时区。
- 统一平台和站点编码。
- 处理字段变更和列名变化。

阶段产出：

- 标准化明细表
- 字段映射文档
- 清洗规则文档
- 异常数据清单

面试表达：

> 第二步不只是把数据放进数据库，还包括源头留痕、清洗和技术标准化。这里主要处理字段、格式、类型、空值、重复、异常值这些问题，让数据先变成结构干净、来源可追溯的标准明细。它解决的是“数据能不能正常用”，不解决父子 SKU、组合品拆分、费用分摊、利润口径这些业务规则。

### 第三步：业务关系与经营口径治理

目标：

把“看的是谁”“怎么算”“分到谁”这三个问题先解决清楚，让 BI 报表建立在统一业务关系、统一经营口径和可信分摊规则之上。

边界说明：

第三步主要解决业务层面的“数据代表什么”。例如同一个产品在不同平台怎么统一，父 SKU 和子 SKU 怎么归集，组合品销售怎么拆到组成单品，费用无法直接匹配到渠道 + 产品时怎么分摊，利润、库存、广告等指标到底按什么口径计算。

核心主数据：

- 产品主数据
- SKU / ASIN / MSKU / FNSKU / 内部 SKU 映射
- 父 SKU / 子 SKU 映射
- 组合品 SKU / 组成单品 SKU 映射
- Kit / Bundle 映射和拆分比例
- 平台和店铺映射
- 站点和国家映射
- 供应商映射
- 品类映射
- 负责人映射
- 费用类型映射
- 成本和分摊规则

阶段产出：

- 主数据表
- 映射关系表
- 映射缺失检查
- 组合品 / 单品拆分规则
- 费用分摊规则表
- 主数据维护流程
- 业务维护责任人

面试表达：

> 第二步解决的是数据格式和质量问题，第三步解决的是业务含义和经营口径问题。我会先解决“看的是谁”，比如 SKU、ASIN、父 SKU、子 SKU、组合品、组成单品、店铺、平台、供应商、品类、负责人这些对象要统一映射；再解决“怎么算”和“分到谁”，比如销售、成本、费用、利润、库存、广告等指标要明确计算规则、数据来源、适用范围和分摊规则。这样后续报表才能被业务、财务和管理层共同信任。

#### 核心指标口径统一

目标：

让业务、财务、运营和管理层对同一个指标有同一个理解。

需要统一的口径：

- 销售额：订单口径、发货口径、结算口径、Retail 口径。
- 成本：采购成本、ERP 成本、移动加权成本、月末成本。
- 费用：平台费用、广告费、仓储费、促销费、Coupon、尾程运费。
- 利润：毛利、经营利润、净利、Contribution Profit。
- 库存：可售库存、在途库存、FBA 库存、海外仓库存。
- 广告：ACOS、TACOS、ROAS、广告归因销售。
- 退货：退款金额、退货率、RMA 原因。

常见分摊场景：

- 费用无法直接匹配到具体渠道 + 产品，比如部分仓储费、尾程运费、平台扣费、促销费用、人工调整费用。
- 广告、促销或费用数据只有账号、活动、账单或月份粒度，无法直接落到 SKU。
- 组合品销售需要拆到组成单品，或者单品成本需要汇总到组合品。
- 父 SKU 维度看经营表现时，需要把多个子 SKU 的销售、库存、费用和利润汇总。

分摊规则设计：

- 按销售额分摊。
- 按销量 / 订单量分摊。
- 按库存数量 / 库存金额 / 可售天数分摊。
- 按重量 / 体积 / 件数分摊。
- 按广告归因销售或活动明细分摊。
- 按业务维护的固定比例分摊。

分摊规则必须保留：

- 分摊依据。
- 适用时间。
- 适用平台 / 店铺 / 品类 / SKU 范围。
- 规则版本。
- 是否需要历史重跑。

阶段产出：

- 指标字典
- 指标公式
- 数据来源说明
- 适用范围说明
- 分摊规则说明
- 口径确认记录

面试表达：

> 第三步可以概括为数据治理和口径治理。主数据解决“对象是谁”的问题，指标口径解决“怎么算”的问题，分摊规则解决“分到谁”的问题。比如利润看起来是一个指标，但背后涉及销售、成本、广告、促销、仓储、尾程、退款等多个来源。有些费用不能直接落到渠道和产品，就要根据销售额、销量、库存、重量、体积或业务规则做分摊。如果这些规则不提前统一，报表上线后只会变成口径争议。

### 第四步：数仓分层和主题数据集建设

目标：

把数据从原始数据逐步加工成稳定、可复用、面向分析的数据集。

为什么要分层：

- 快速定位问题：如果报表数字不对，可以沿着 ADS、DWS、DWD、DIM、ODS 往前追，判断问题出在源数据、清洗、映射、汇总、指标公式还是报表展示。
- 降低维护成本：清洗、映射、分摊、汇总逻辑沉淀在数仓层，不需要每张 Power BI 报表重复写一遍。
- 提升复用能力：销售、广告、库存、费用、成本等主题数据集可以被多个报表、预警和分析任务复用。
- 减少 BI 加载数据量：Power BI 不直接加载大量原始明细，而是加载面向分析的主题数据集或必要明细。
- 提升使用体验：报表打开更快、筛选更顺、刷新更稳定，业务用户使用体验更好。
- 提升查询效率：把复杂计算前置到数据库或数仓层，减少 Power BI 端临时计算压力。

推荐分层：

#### ODS：原始数据层

做什么：

- 保留平台后台、ERP、财务系统、广告后台、人工表、线上导出表等原始数据。
- 保留来源系统、来源文件、导入批次、导入时间、数据日期范围。
- 尽量不做复杂业务加工，主要保证源数据可追溯。

为什么需要：

- 后续数据被质疑时，可以追溯到原始来源。
- 源文件导错、日期选错、重复导入时，能快速定位。
- 支持历史重跑和对账。

#### DIM：维度层

做什么：

- 维护产品、SKU、ASIN、父子 SKU、组合品、平台、店铺、站点、供应商、品类、负责人、时间、币种等维度。
- 维护映射关系、归属关系和分摊配置。

为什么需要：

- 统一“看的是谁”的问题。
- 让不同来源的销售、库存、广告、费用、成本可以按同一套维度分析。
- 避免每张报表都临时维护一套映射。

#### DWD：明细事实层

做什么：

- 把 ODS 原始数据清洗成标准明细事实。
- 形成销售明细、广告明细、库存快照、费用明细、成本明细、退货明细等。
- 保留足够细的颗粒度，便于追溯和二次加工。

为什么需要：

- 统一明细层口径，避免源系统字段差异直接影响分析。
- 支持异常排查和明细对账。
- 为 DWS 主题汇总提供稳定输入。

#### DWS：主题汇总层

做什么：

- 按业务主题进行汇总，例如经营利润、库存周转、广告表现、费用分析、供应商表现、退货质量。
- 把常用统计口径、分摊结果和业务汇总逻辑沉淀下来。

为什么需要：

- 让业务分析不必每次从明细重新计算。
- 降低 Power BI 需要加载和计算的数据量。
- 提升报表刷新速度和查询效率。

#### ADS：应用层

做什么：

- 面向具体应用准备数据，比如 Power BI 经营驾驶舱、库存看板、广告看板、费用看板、预警平台。
- 字段命名更贴近业务，颗粒度和权限字段更适合展示层使用。

为什么需要：

- 让 Power BI 直接连接更稳定、更轻量、更贴近业务的数据集。
- 支持不同报表主题、不同用户角色和不同权限范围。
- 减少报表层复杂逻辑，提升使用体验。

阶段产出：

- 分层表结构
- 主题数据集
- 数据血缘说明
- 调度任务
- 对账脚本或校验逻辑

面试表达：

> 我会把数据分成 ODS、DIM、DWD、DWS、ADS 几层。ODS 保留原始数据和批次，DIM 维护主数据和映射关系，DWD 做标准化明细，DWS 做业务主题汇总，ADS 直接服务 Power BI 和预警应用。这样做的好处是数据链路清楚，出问题时能快速定位；复杂清洗、映射、分摊和利润计算不会都堆在 Power BI 里；同时可以减少 BI 加载的数据量，提升报表刷新速度、查询效率和业务使用体验。

### 第五步：BI 数据建模及报表开发

目标：

在 BI 层建立稳定、复用、口径统一的数据模型，并基于这个模型开发面向管理层、运营、财务、供应链等角色的经营分析报表。

关键设计：

- 一般采用星型模型。
- 通过主数据维度去关联不同业务主题的事实表。
- 维度表承载日期、产品、SKU、ASIN、平台、店铺、品类、供应商、负责人等筛选、分组和下钻维度。
- 事实表承载销售、广告、库存、费用、成本、退货、目标等不同业务主题的数据。
- 度量值集中管理。
- 不同报表复用同一个语义模型。
- 避免每张报表复制一套模型。

BI 层和数据底层的分工：

- 数据底层负责：采集、落库、清洗、技术标准化、主数据映射、组合品拆分、费用分摊、主题汇总。
- BI 层负责：数据建模、表关系设计、DAX 度量值、高级运算、筛选交互、钻取分析和报表开发。
- 不建议把大量清洗、映射、分摊、汇总逻辑都放在 Power BI 里，否则会影响刷新速度、模型复用、口径一致性和维护成本。

BI 层常见高级运算：

- 同比、环比、累计、滚动周期。
- 毛利率、利润率、ACOS、TACOS、ROAS、库存周转率等派生指标。
- 平台、店铺、SKU、品类、负责人等维度排名。
- 目标达成率、贡献占比、费用占比、异常波动。
- 动态筛选、下钻、钻取、Top N、条件格式。

阶段产出：

- BI 数据模型
- DAX 度量值
- 事实表和维度表关系
- 指标说明
- 可复用数据集
- 经营分析报表
- 角色化看板

面试表达：

> BI 层我会重点做数据建模和报表开发，而不是把所有前期加工都放进 Power BI。好的 BI 平台应该在数据底层完成清洗、映射、分摊和主题汇总，BI 层主要用主数据维度去关联销售、库存、广告、费用、成本等事实表，一般采用星型模型。这样维度表负责筛选和下钻，事实表负责承载业务数据，DAX 主要做同比环比、占比、排名、利润率等高级运算，报表层再面向不同角色做经营分析展示。

#### 可视化报表和经营分析看板建设

目标：

根据不同角色设计报表，让数据能真正支持经营动作。

典型看板：

- 管理层经营驾驶舱
- 经营利润看板
- 平台 / 店铺 / SKU 分析
- 库存周转看板
- 广告效率看板
- 费用与对账看板
- RMA / 退货看板
- 供应商管理看板
- 目标达成与绩效看板

设计原则：

- 管理层看趋势、结构、排名和异常。
- 运营看 SKU、库存、广告、促销和责任人。
- 财务看费用、账单、差异和可追溯明细。
- 供应链看库存、周转、断货、超龄和供应商。

阶段产出：

- 报表矩阵
- 页面原型
- Power BI 报表
- 管理层驾驶舱
- 明细追踪页面

面试表达：

> 第五步是 BI 数据建模及报表开发。建模解决不同主题事实表和主数据维度之间的关系，报表解决业务使用和经营分析。报表设计要按角色和业务动作来做，管理层看经营结果和异常，运营定位 SKU 和动作，财务看明细和对账，供应链看库存和供应商表现。

### 第六步：T+1 更新、权限控制与数据质量校验

目标：

让平台每天稳定产出最新经营数据，并且做到“该看到的人能看到，不该看到的人看不到”。业务侧每天上班可以直接查看昨天或最新一批销售、利润、库存、广告、费用数据，不需要再等人工整理；不同渠道、产品线、运营负责人只能看到自己负责范围内的数据。

T+1 更新：

- 每天固定时间完成前一天数据采集、入库、加工和 Power BI 刷新。
- 核心报表尽量在上班前刷新完成，让管理层和运营一早就能看到最新经营结果。
- 对 API、爬虫、自动化程序、后台导出、人工维护数据分别设置到达检查。
- 对关键表记录最后更新时间、数据日期范围、批次号和刷新状态。
- 刷新失败、源文件未到、数据延迟时要有提醒，避免业务拿旧数据做判断。
- 大表可以采用增量刷新或按日期分区，减少每日刷新压力。

权限控制：

- Workspace 权限
- App 分发
- RLS 动态行级权限
- 按渠道、平台、店铺、站点、产品线、品类、SKU、负责人控制可见范围
- 渠道运营只能看自己负责渠道的数据
- 产品线运营只能看自己负责产品线的数据
- 管理层、财务、数据管理员根据岗位开放更高层级或全量权限
- 人员变动、产品线调整、渠道负责人变化时，只维护权限映射表，尽量不改报表本身

数据质量：

- 源文件是否到达
- 日期范围是否正确
- 是否重复导入
- 必填字段是否缺失
- SKU 映射是否缺失
- 成本是否缺失
- 汇率是否缺失
- 金额和销量是否异常波动
- 结果是否能和平台、ERP、财务账单对上

阶段产出：

- T+1 刷新计划
- 刷新日志和失败提醒
- 权限表
- RLS 规则
- 数据质量检查表
- 异常提醒机制
- 对账报告

面试表达：

> BI 平台上线前，我会重点关注 T+1 更新、权限控制和数据质量。T+1 的目标不是简单地让刷新任务跑起来，而是保证业务每天上班就能看到昨天或最新一批经营数据。权限上会按渠道、产品线、店铺、SKU、负责人这些维度控制可见范围，比如不同渠道或产品线的运营只能看到自己负责的数据。数据质量上还要检查文件有没有到、日期有没有错、是否重复导入、SKU 映射和成本有没有缺失，这些都会影响最终结果。

### 第七步：上线运营、业务反馈和持续迭代

目标：

让 BI 平台成为长期可维护的经营工具，而不是一次性项目。

运营机制：

- 建立需求收集和优先级机制。
- 建立指标口径维护机制。
- 建立权限变更流程。
- 建立报表版本管理。
- 监控刷新失败和使用情况。
- 收集业务反馈。
- 定期复盘报表是否还被使用。
- 把高频人工分析沉淀为正式报表或预警。

阶段产出：

- 使用说明
- 指标字典
- 需求池
- 版本记录
- 用户反馈记录
- 报表下线和合并机制

面试表达：

> BI 平台不是上线就结束，后续要持续运营。比如哪些报表真正被使用，哪些指标口径变化，哪些业务问题需要沉淀成新主题，哪些临时分析可以转成预警。这些机制决定了平台能不能长期可用。

## 权威参考框架

这个流程结合三类经验：

- Microsoft Power BI / Fabric 官方实施建议：战略规划、治理、COE、语义模型、星型模型、刷新、部署流水线。
- 数据仓库通用方法：ODS、DIM、DWD、DWS、ADS 分层，事实表和维度表建模，数据质量和血缘管理。
- 跨境电商业务实践：Amazon VC/SC、多店铺、多平台、ERP、广告、库存、费用、利润、人工维护映射表和 T+1 经营分析。

可引用的官方原则：

- Power BI 语义模型应优先采用星型模型，事实表用于度量，维度表用于筛选、分组和下钻。
- 当数据量大、转换复杂、存在缓慢变化维度或复杂业务规则时，应优先建设数据仓库和 ETL，再由 Power BI 连接数据仓库。
- 企业级 BI 建设需要考虑治理、内容所有权、交付范围、COE、权限、安全、部署和审计，而不是只关注单个报表。
- 对经常增长的大事实表，应考虑增量刷新，降低刷新耗时和资源消耗。

## 阶段一：明确业务目标和建设边界

### 1. 先问清楚平台要解决什么问题

跨境电商 BI 平台通常不是为了“可视化”，而是为了解决这些经营问题：

- 管理层每天是否能看到公司、平台、店铺、SKU、品类维度的利润表现？
- 哪些 SKU 销售好但利润差？
- 哪些费用异常侵蚀利润？
- 哪些库存有断货风险或超龄风险？
- 广告花费是否失控，ACOS / TACOS 是否异常？
- 促销费用、Coupon、平台扣费是否能和账单对上？
- RMA、差评、退货是否影响产品质量判断？
- 目标达成、绩效核算是否有统一口径？
- Amazon VC 的 PO、DI、DF、Retail Sales、Chargeback、Coop、Shortage Claim 等是否能拆清？

### 2. 建设边界不要一开始铺太大

推荐按优先级分三期：

#### 第一期：经营利润核心闭环

目标：让管理层能看清楚销售、成本、费用和利润。

核心主题：

- 销售
- 成本
- 平台费用
- 广告费
- 促销费
- 仓储费
- 尾程运费
- 毛利 / 净利

#### 第二期：运营效率和风险监控

目标：让业务团队能发现库存、广告、退货、竞品和异常风险。

核心主题：

- 库存周转
- 可售天数
- 超龄库存
- 广告 ACOS / TACOS
- Buy Box
- Listing 排名
- 差评
- RMA 退货
- 竞品价格

#### 第三期：管理机制和自动化运营

目标：让数据平台从看板升级为经营管理系统。

核心主题：

- 目标达成
- 绩效监控
- 供应商管理
- 自动预警
- 自动化对账
- 权限分发
- 业务闭环跟进

## 阶段二：数据源盘点

### 1. 按业务域盘点数据源

建议建立一张“数据源清单”，每个数据源都记录：

- 数据源名称
- 所属平台
- 业务域
- 获取方式
- 更新频率
- 数据粒度
- 时间字段
- 主键或唯一键
- 是否可追溯源文件
- 负责人
- 常见异常

### 2. 跨境电商常见数据源

## 阶段三：主数据治理

### 1. 为什么主数据是核心

跨境电商 BI 项目里，报表难点经常不是图表，而是映射关系。

常见问题：

- 同一个产品在不同平台有不同 SKU。
- Amazon 上有 ASIN、MSKU、FNSKU、Vendor Code、内部 SKU。
- Kit / Bundle 和单品成本、库存、销量需要拆分或归集。
- 同一个 SKU 可能归属不同供应商、品类、负责人。
- 历史数据中映射关系会变化。
- 平台费用和广告数据不一定能直接对应内部 SKU。

### 2. 核心主数据表

建议至少建立：

- `dim_product`：内部产品主数据
- `dim_sku_mapping`：平台 SKU / ASIN / MSKU / 内部 SKU 映射
- `dim_account`：平台、账号、店铺、站点
- `dim_channel`：业务模式，如 Amazon VC PO / DI / DF、SC、3P、DTC
- `dim_vendor`：供应商
- `dim_category`：品类
- `dim_owner`：负责人
- `dim_date`：日期
- `dim_currency_rate`：汇率
- `dim_cost_rule`：成本规则
- `dim_fee_mapping`：费用类型映射
- `dim_allocation_rule`：费用分摊规则

### 3. 主数据维护机制

主数据不能只靠数据人员手工改 SQL，应该有维护机制：

- 业务负责人维护源头信息。
- 数据团队定义字段、校验规则和版本。
- 关键映射变更保留历史。
- 缺失映射要能被数据质量检查发现。
- 新 SKU / 新平台 / 新店铺上线前先补主数据。

面试表达：

> 我会把主数据维护当成 BI 平台的基础设施。因为很多利润不准、库存不准、费用归属不准，本质上不是 Power BI 问题，而是 SKU、平台、供应商、负责人这些映射关系没有稳定维护。

### 3. 利润口径要特别谨慎

跨境电商利润经常不是一个字段，而是多个数据源组合：

```text
经营利润
= 销售收入
- 商品成本
- 平台费用
- 广告费
- 促销费
- 仓储费
- 尾程运费
- 退款和退货相关费用
- 其他可归属费用
```

需要明确：

- 销售用订单口径还是结算口径？
- 成本用采购成本、移动加权成本还是 ERP 月末成本？
- 广告费按点击日期、订单日期还是归因日期？
- 仓储费按 SKU 直接归属还是按库存占比分摊？
- 促销费按活动、ASIN、SKU 还是账单归属？
- 汇率用日汇率、月均汇率还是财务汇率？
- 尾程运费是否按订单、重量、体积、销售额分摊？

面试表达：

> 利润 BI 最重要的是先把口径讲清楚。不同部门可能对销售、费用、成本的归属理解不同，如果不提前统一，后面每次看利润都会变成口径争议。所以我会先建立指标字典和费用归属规则，再做模型和报表。

## 阶段五：数仓分层设计

### 1. ODS：原始数据层

目标：

保留原始数据和来源痕迹，不在这一层做过多业务加工。

关键字段：

- source_system
- source_platform
- account
- marketplace
- business_mode
- source_file_name
- batch_id
- imported_at
- report_start_date
- report_end_date

价值：

- 方便追溯。
- 方便重跑。
- 方便发现源数据变化。
- 避免后续争议时找不到原始依据。

### 2. DIM：维度层

目标：

建立统一分析维度，让不同来源数据可以被同一套维度筛选和下钻。

典型维度：

- 产品
- SKU 映射
- 平台
- 店铺
- 站点
- 供应商
- 品类
- 负责人
- 时间
- 币种
- 费用类型

### 3. DWD：明细事实层

目标：

把原始数据清洗成标准化明细事实表，保留足够细的颗粒度。

典型事实表：

- `fact_sales_order`
- `fact_sales_retail`
- `fact_vc_po`
- `fact_ad_performance`
- `fact_inventory_snapshot`
- `fact_fee_detail`
- `fact_promotion_detail`
- `fact_cost_detail`
- `fact_rma_return`

注意：

VC Order、Retail Sales、PO、DI、DF 不要盲目合并。应该保留 source、channel、business_mode，再在 DWS 或 ADS 层按明确口径汇总。

### 4. DWS：主题汇总层

目标：

沉淀可复用的业务主题宽表或汇总表，减少 Power BI 里重复加工。

典型主题：

- 日 SKU 平台利润汇总
- 月店铺利润汇总
- SKU 库存周转汇总
- 广告 Campaign 表现汇总
- 促销费用汇总
- 供应商表现汇总
- RMA 退货汇总

### 5. ADS：应用服务层

目标：

直接服务 Power BI 语义模型、预警平台、管理层驾驶舱。

特点：

- 字段命名友好。
- 颗粒度明确。
- 指标口径稳定。
- 权限字段齐全。
- 适合报表刷新。

面试表达：

> 我的理解是，Power BI 里不应该承载太多底层清洗逻辑。Power BI 更适合做语义模型、指标计算和展示交互。复杂清洗、主数据映射、费用分摊、利润计算，最好尽量前置到数据库或数仓层，这样可维护性和可信度更高。

## 阶段六：Power BI 语义模型设计

### 1. 采用星型模型

Power BI 模型建议以星型模型为主：

```text
维度表：日期、产品、平台、店铺、品类、供应商、负责人
        ↓
事实表：销售、广告、库存、费用、成本、退货、目标
```

原则：

- 事实表放数值和业务事件。
- 维度表放筛选、分组、下钻字段。
- 避免在 Power BI 模型里堆很多大宽表互相关联。
- 避免事实表和事实表直接多对多关联。
- 共享维度统一筛选多个事实表。

### 2. 数据模型分层

建议在 Power BI 中区分：

- 数据集 / 语义模型：统一指标和关系。
- 报表：只负责展示和交互。
- 仪表板或 App：负责分发给不同用户。

不要每个报表都复制一套数据模型，否则会造成：

- 指标重复定义。
- 口径不一致。
- 刷新压力大。
- 权限难维护。
- 后续修改成本高。

### 3. DAX 指标设计

DAX 指标要分层：

基础指标：

- 销售额
- 成本
- 广告费
- 订单量
- 销量

派生指标：

- 毛利
- 毛利率
- ACOS
- TACOS
- 库存周转
- 可售天数

业务指标：

- 经营利润
- 经营利润率
- 目标达成率
- 异常费用率
- 广告效率分层

命名规范：

- 中文业务名称对业务用户友好。
- 技术字段保持英文或统一命名。
- 度量值集中管理。
- 不同口径要在名称或说明里区分。

### 4. Power Query 使用边界

Power Query 适合：

- 轻量字段清洗。
- 类型转换。
- 简单合并。
- 小型维表维护。

不建议把大量复杂逻辑都放在 Power Query：

- 大数据量清洗。
- 多步骤复杂分摊。
- 历史重跑。
- 多报表复用逻辑。
- 复杂主数据映射。

这些更适合放在数据库、ETL 或数仓层。

## 阶段九：刷新和性能

### 1. 刷新策略

按业务需求分层：

- 管理层经营看板：每日 T+1。
- 广告和库存风险：每日或更高频。
- 财务账单：按账单周期或文件到达时间。
- 成本和汇率：按日、月或财务周期。
- 目标和人工维护表：按维护频率。

### 2. 增量刷新

适合增量刷新的表：

- 销售明细
- 广告明细
- 费用明细
- 库存快照
- 订单明细

不一定适合增量刷新的表：

- 小型维度表
- 经常整体变化的映射表
- 需要全量重算的分摊结果

### 3. 性能优化原则

- 大表尽量在数仓层预汇总。
- Power BI 模型采用星型模型。
- 减少不必要列。
- 避免高基数字段进入展示模型。
- 避免复杂 DAX 重复计算。
- 合理使用增量刷新。
- 将通用逻辑前置到数据库。
- 区分 Import、DirectQuery、混合模式使用场景。

面试表达：

> 我会把 Power BI 当成语义层和展示层，而不是所有清洗计算都放进去。性能优化最有效的方式往往不是调图表，而是前面建模正确、字段精简、事实维度关系清楚、刷新策略合理。

## 阶段十：数据质量和验收

### 1. 数据质量检查

建议建立每日检查：

- 文件是否到达。
- 数据日期是否正确。
- 是否重复导入。
- 核心字段是否为空。
- SKU 映射是否缺失。
- 金额是否异常波动。
- 销量是否异常波动。
- 费用是否异常波动。
- 汇率是否缺失。
- 成本是否缺失。
- 利润是否出现异常负值。

### 2. 对账机制

至少要和这些来源对账：

- 平台后台总销售额
- ERP 销售或成本
- 广告后台花费
- 财务账单
- 库存后台
- 人工月报或历史报表

### 3. 验收标准

一个 BI 平台能不能上线，不只看页面是否完成。

验收应包括：

- 指标口径已确认。
- 核心报表与源系统总数能对上。
- 权限测试通过。
- 刷新任务稳定。
- 异常数据有提示。
- 业务用户知道怎么使用。
- 口径文档已沉淀。
- 问题反馈机制明确。

## 阶段十一：发布、治理和运营

### 1. 环境分层

推荐至少区分：

- 开发环境
- 测试环境
- 生产环境

Power BI 中可以通过不同 Workspace 或部署流水线管理。

### 2. 内容发布流程

建议流程：

```text
需求提出
  ↓
业务口径确认
  ↓
数据源和可行性评估
  ↓
模型开发
  ↓
报表开发
  ↓
数据对账
  ↓
业务验收
  ↓
权限配置
  ↓
生产发布
  ↓
使用反馈和迭代
```

### 3. COE 或数据治理机制

如果公司规模变大，需要建立类似 BI COE 的机制：

- 统一指标口径。
- 统一报表规范。
- 管理语义模型。
- 管理权限和数据安全。
- 指导业务自助分析。
- 收集需求优先级。
- 监控使用率和刷新失败。
- 推动数据文化。

面试表达：

> BI 平台上线只是开始，不是结束。后续需要运营机制，包括需求优先级、指标口径维护、权限变更、刷新监控、用户反馈和版本管理。否则平台很容易变成一堆没人维护的报表。

## 面试中的完整回答版本

如果面试官问：

> 你如果从 0 到 1 给一家多平台跨境电商公司搭建 Power BI 数据平台，会怎么做？

可以这样回答：

> 我不会一开始就进入 Power BI 做图，而是先分几步推进。
>
> 第一步是明确业务目标和一期范围。跨境电商 BI 平台通常要解决经营利润、库存周转、广告效率、费用管控、退货质量和目标达成这些问题，但一期不能铺太大，我会优先做经营利润核心闭环。
>
> 第二步是数据落库、清洗和技术标准化。多平台公司数据一般来自 Amazon VC、SC、其他平台、ERP、广告后台、库存系统、财务账单和人工维护表。拿到这些数据后，我会先保留来源、批次和文件痕迹，再处理字段格式、日期、币种、空值、重复和异常值，让数据先变成结构干净、来源可追溯的标准明细。
>
> 第三步是做业务关系和经营口径治理。这里才处理业务含义，核心是解决“看的是谁”“怎么算”“分到谁”三个问题。比如 SKU、ASIN、MSKU、父子 SKU、组合品和单品这些对象要统一映射，同时建立销售、成本、费用、利润、库存、广告等核心指标字典，明确每个指标的数据来源、计算规则、适用范围和分摊规则。这里也要特别注意 Amazon VC 的 Order、Retail、PO、DI、DF 口径不能直接混在一起，需要保留来源和业务模式。
>
> 第四步是搭建数据分层。我会按 ODS、DIM、DWD、DWS、ADS 的思路建设。ODS 保留原始数据和批次，DIM 做主数据，DWD 做标准明细事实，DWS 做主题汇总，ADS 服务 Power BI 模型和报表。
>
> 第五步是做 BI 数据建模及报表开发。模型上一般采用星型模型，通过主数据维度去关联销售、广告、库存、费用、成本等不同业务主题的事实表。底层已经完成清洗、映射、分摊和主题汇总，BI 层主要做 DAX 高级度量、筛选下钻和报表开发。报表上按用户角色设计，管理层看经营驾驶舱，运营看 SKU、库存、广告，财务看费用和对账，供应链看库存和供应商。
>
> 第六步是做 T+1 更新、权限控制和数据质量校验。T+1 更新要保证业务每天上班就能看到昨天或最新一批经营数据；权限上通过权限表结合 RLS，按渠道、产品线、店铺、SKU、负责人控制可见范围，让不同渠道或产品线的运营只能看到自己负责的数据；同时做文件到达、重复导入、映射缺失、金额波动、成本缺失等检查，保证结果可信。
>
> 最后是发布和运营机制。BI 平台上线不是结束，还要有口径文档、需求优先级、刷新监控、权限变更、业务反馈和版本管理。这样它才不是一堆报表，而是一套长期可用的经营数据平台。

## 面试追问准备

### 追问一：为什么不直接在 Power BI 里处理所有数据？

建议回答：

> Power BI 可以做一部分清洗和建模，但跨境电商多平台利润分析涉及数据源多、数据量大、映射复杂、费用分摊和历史重跑。如果都放在 Power BI 里，后续性能、复用、对账和维护都会有问题。我更倾向把复杂清洗、主数据映射和利润计算前置到数据库或数仓层，Power BI 主要负责语义模型和展示交互。

### 追问二：从 0 到 1 最大难点是什么？

建议回答：

> 最大难点不是可视化，而是业务口径和基础数据。比如 Amazon VC 不同报表口径不同，SKU 和 ASIN 映射不完整，费用归属不清楚，成本和汇率更新不及时，这些都会影响利润可信度。只有先把这些问题解决，BI 才能真正被业务信任。

### 追问三：怎么保证数据准确？

建议回答：

> 我会分三层保证。第一是源头校验，比如文件是否到达、日期范围是否正确、是否重复导入。第二是加工过程校验，比如 SKU 映射缺失、成本缺失、费用异常波动。第三是结果对账，比如销售额和平台后台对，广告费和广告后台对，费用和财务账单对，利润结果和历史报表或财务结果做抽样核对。

### 追问四：如何设计权限？

建议回答：

> 我会先明确权限维度，比如部门、岗位、平台、店铺、站点、品类、负责人。然后建立权限映射表，把用户邮箱和可见范围维护起来，再结合 Power BI 的 RLS 做动态权限。这样后续人员或范围变化时，不需要频繁改报表，只需要维护权限表。

### 追问五：如果业务临时要很多报表怎么办？

建议回答：

> 我会先判断需求属于临时分析、已有主题扩展，还是新业务主题。如果是临时分析，可以快速支持；如果会长期使用，就要沉淀到语义模型和报表体系里。同时要做需求优先级管理，优先支持能影响经营决策的主题，而不是无限堆报表。
