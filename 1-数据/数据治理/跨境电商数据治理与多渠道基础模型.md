# 跨境电商数据治理与多渠道基础模型

## 为什么需要治理层

跨境电商 BI 项目的复杂度不只在 SQL，而在多来源、多口径、多渠道和人工文件并存。没有治理层时，T+1 利润即使每天刷新，也可能因为源文件重复、Mapping 缺失、渠道串数、默认规则变化而变得不可信。

## 当前治理对象

- `bi_source_registry`：来源、渠道、业务口径、粒度、日期语义、频率、SLA、责任人和导入脚本。
- `bi_ingestion_batch`：文件哈希、批次、日期范围、行数、目标表和处理状态。
- `bi_data_quality_rule`：可执行数据质量规则登记。
- `bi_data_quality_run`：每次检查的 PASS / WARN / FAIL、影响行数和金额。
- `bi_special_rule_config`：特殊映射、有效期、优先级、原因和 CR。
- `dim_channel_context`：渠道、业务范围、来源系统、PO/DF/DI 等业务模式、账号、市场和币种。

## 多渠道边界

- `Amz VC retail/endpos` 是当前利润销售事实。
- `Amz VC supply/order` 按 PO / DF / DI 独立保存，只用于供货结构、Coop 和成本权重。
- `Amz SC seller/order`、`Walmart retail/order` 当前为 planned，未经来源、Mapping、质量和利润验收，不得进入 VC 利润表。
- 共享库存、原始 COGS、Kit、NS 映射和尺寸不整表贴渠道；进入利润事实时再按明确规则继承渠道上下文。

## 手工文件治理流程

1. 文件进入已登记的 source 目录。
2. 使用脚本计算 SHA-256 并登记批次。
3. 重复哈希默认拒绝，避免重复导入。
4. 正式导入脚本写目标表。
5. 更新批次状态、日期范围、行数和错误信息。
6. 运行质量检查和自动状态快照。

## 必填口径维度

每个新事实表或指标都应明确：

- `channel`
- `business_scope`
- `source_system`
- `grain`
- `date_semantics`
- `currency`
- `account/vendor`
- `market`

即使字段尚未全部落库，也要在规则或变更单中说明。

## 核心经验

治理不是项目最后的文档补充，而是利润数据可信的前置条件。尤其是 T+1 利润项目，任何一个源文件延迟、重复、缺字段、Mapping 缺失或渠道串数，都可能让利润刷新“准时但错误”。
